## 一手资料复核

- [MiniMax 视频生成指南](https://platform.minimaxi.com/docs/guides/video-generation)：公开工作流为异步创建任务、查询结果；并列说明 H3 与 H3 Max。
- [官方创建接口](https://platform.minimaxi.com/docs/api-reference/video-generation-v2-create)：文生视频可以指定画幅，首尾帧模式的画幅由输入图片决定。首尾帧与角色参考是不同模式。
- [官方查询接口](https://platform.minimaxi.com/docs/api-reference/video-generation-v2-query)：结果包含任务状态及成片地址；查询结果不等于已播放。
- [官方取消/删除接口](https://platform.minimaxi.com/docs/api-reference/video-generation-v2-delete)：同一操作可能取消排队任务，也可能删除终态记录。因此不能将“改主意”无条件映射成 DELETE。
- [fal Director 会话协议](https://fal.ai/models/minimax/h3-max/director/api)：提供 WebRTC 及方向更新，属于不同部署契约。本轮仅作对照，没有切换供应商或启用 fal。

本次核验的是上述公开文档，不推断未公开或账号专属接口是否存在，不把模型名中的 Max 自动等同于 Director。

## 本轮代码交付

1. 官方请求构建：模型约束、输入用途、时长、分辨率和画幅校验；默认桌面横屏。输入首尾帧时要求确认 adaptive，避免把竖图送入后仍承诺横屏。仅支持本轮覆盖的文字/首尾帧子集，未知字段拒绝而非忽略。
2. 服务端任务工厂：复用供应商—模型绑定，创建与单次查询通过官方地址进行。无隐式供应商切换、循环轮询、自动重试、自动删除或媒体下载。
3. 提交状态不确定单独处理：网络中断、异常回执和部分服务错误不当成“确定没有生成”，也不自动再花一次钱。
4. 供应商异常正文不直接透出；任务编号、模型、输出地址与结构校验后才交给后续调用方。

## 参与感如何接在这层之上

- **我说了什么：** 保存玩家原始表达及来源情境，不先把它解释为已经成功的行为。
- **下一幕准备什么：** 由编排层建立候选与行动的关联，带版本；用户改主意后，已失效候选不因晚到而强行播放。
- **我真正看到了什么：** 根据播放证据与语义复核决定是否兑现行动。生成完成回执只表示候选可用。
- **世界记住了什么：** 只提交通过检查且已呈现的结果；意图、计划和事实分开。

这四步仍需运行时实现和模型实测，当前任务适配器不自动具备事件等待、记忆或画面语义检查能力。

## 三个重要产品边界

1. **桌面构图与用户图片。** 人物参考图和开场整帧不混用。若用户希望横屏现场，首帧也需适合横向构图；不是悄悄裁切人物，也不是传一个横屏 ratio 就保证结果。
2. **改主意与费用。** 放弃旧候选不等于供应商取消旧任务，更不等于已发生费用退回。当前不实现高风险的自动 DELETE 路径。
3. **实时体验与任务接口。** 本轮没有以逐段点播替代用户的实时目标。正式开场仍保持门禁，直到连续调度、播放切换、响应时延、玩家决定权及服务端预算通过验收。

## 后续单一里程碑

验证“自动开场 → 非预设自由行动 → 真实相关画面 → 下一次关键等待”。先做官方任务链路的受控技术实验，再决定该部署能否满足实时体验；若证据不足则保持未通过状态，不以播放动画或循环旧视频作为成功结果。

已有 UI 不增加假事件卡、假反应或未启用的语音按钮。二期的空间点击仍延后，角色和世界状态应保持供应商无关。
