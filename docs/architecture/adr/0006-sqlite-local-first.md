# ADR-0006：SQLite 本地优先与单 runtime 数据所有权

## 状态

Proposed · 2026-09-10。用户已明确选择前期 SQLite；本文的运行、可靠性及迁移细节等待技术评审，不代表实施完成。

## 背景

产品首先需要本地可开发、可恢复的单用户视频经历，不应为起步引入数据库服务器集群。现有业务真值散在两套原型的浏览器存储中；长期视频任务与费用又不能依赖页签存活。未来仍计划托管 Web 与桌面，因此不能让页面直接耦合数据库文件。

## 决策

一个常驻 runtime 拥有 Prisma/SQLite、任务、素材和凭证；Next 与后续 Tauri 都经契约访问。SQLite 存业务元数据/版本/任务/账本，媒体走本地 AssetStore。领域规则依赖仓库 port 而非 Prisma client。文件放本机持久数据目录，使用短事务、已验证 WAL/驱动版本、CAS、任务幂等与一致性备份。

前期使用正式 SQLite 文件做开发与恢复测试，不采用开发 SQLite、生产 PostgreSQL 却共用一份迁移 SQL 的隐式双轨方案。PostgreSQL 到需要托管/多实例写入时再建立独立迁移和数据切换流程。

## 后果

### 正面
- 本机启动轻，不先维护数据库服务；Web 与桌面共用数据用例。
- 原型转产品时有唯一保存位置，重启恢复和冲突可测试。
- 替换存储主要影响基础设施与迁移，不重写界面与剧情规则。

### 代价
- 多一个常驻 runtime 进程及桌面打包责任；SQLite 仍受单写者约束。
- 媒体与数据库需协调备份/垃圾回收，不存在天然跨文件事务。
- 本地文件不自动跨设备同步，也不适合作 Vercel Functions 的共享持久库。
- PostgreSQL 切换仍是数据工程工作；仓库接口只减小影响，不消灭迁移成本。

## 比较过的方案

- localStorage/IndexedDB 真值：保留为草稿/缓存，缺乏服务端任务、统一授权与事务账本。
- PostgreSQL 首发：后期合理，当前增加本地运维，不符合用户明确选择。
- Next 路由直接写库并调度：代码少，但热更新、请求生命周期、桌面复用与任务归属不清。
- 每个桌面窗口自带数据库插件：破坏统一用例/任务拥有者，不采用。
